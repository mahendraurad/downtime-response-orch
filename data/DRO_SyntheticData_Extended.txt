MERGE RATIONALE
  TABLE 1: Location adds only plant/area/timezone to a line — 2 rows, no FK joins needed.
           Merged as extra columns on the line record.
  TABLE 2: Sensor channels are one-to-one with bearings in this dataset. Channel metadata
           (historian tag, valid range, sample rate) and baseline stats (mean/std per signal)
           are bearing-level properties. Merging eliminates two join steps for every agent
           that needs "what is the baseline for this bearing's channel?"
  TABLE 6: LOTO and technician data are always read together — the Safety Agent checks the
           permit, then checks whether the assigned crew are qualified for it. Two rows per
           asset-permit pair with technician info embedded removes the join.
  TABLE 7: Maintenance windows and production schedule are both read by the Prescriptive Agent
           in a single decision step: "is this window approved AND does it align with the
           active shift?" Merging into one operational context table removes the join.
  TABLE 9: Historical work orders, execution log, and learned cases all describe the same
           completed event from three angles (what was done / how the agent decided / what
           was confirmed). One row per case with all three perspectives as columns is simpler
           and sufficient for the baseline. Expand to separate tables when volume requires.

PRE-LOADED vs AGENT-DERIVED
  All 9 tables = pre-loaded ground truth.
  The following are created by agents at runtime — leave empty at start:
    anomaly_event, signal_quality_event, fault_diagnosis, risk_assessment,
    maintenance_recommendation, maintenance_case, work_order (new), agent_execution_log
